# ADR — Architecture Decision Records (формат документации)

Решение по GitHub issue #7: «перенести наработки (диаграммы, ТЗ) в единый формат документа, читаемый GitHub».

## ADR-001: Единый формат — Markdown + Mermaid

- **Решение**: все артефакты переносятся в `.md` под `docs/`. Диаграммы drawio → Mermaid code-fences (GitHub рендерит нативно, без внешних сервисов).
- **Почему**: цель issue — «лучше чтобы читался гитхабом». Markdown — единственный формат, который:
  - рендерится на GitHub (в т.ч. Mermaid, таблицы, code-fence);
  - открывается диффом (code review документации на PR);
  - не требует сторонних инструментов для просмотра.
- **Отклонено**: ASCII-арт (нечитаем при изменениях), встраивание PNG drawio (не git-friendly, не диффится), оставить только .drawio (не рендерится, цель issue не достигнута).
- **Ограничение**: Mermaid передаёт логику потока; декоративные элементы drawio (рамки, легенда) — как Markdown-таблицы и списки рядом с диаграммой.

## ADR-002: Исходники сохраняются

- **Решение**: `.docx` и `.drawio` перемещаются в `docs/sources/` и считаются источником истины. `.md` — зеркала с провенансом (шапка «источник: <файл, страница>»).
- **Почему**: docx и drawio — единственные авторитетные артефакты; без их сохранения теряется история. При расхождении верен оригинал.
- **Следствие**: двухсторонней синхронизации пока нет (односторонняя: оригиналы → markdown). Смена в одном месте — ручное обновление зеркала.

## ADR-003: Неоднозначности ТЗ — Decisions

- **Решение**: каждая трактуемая двояко формулировка ТЗ явно фиксируется как **Decision** в `walking-skeleton.md` (раздел «Decisions») с обоснованием. Ничего не решается молча.
- **Почему**: диаграммы пошли дальше ТЗ (OTP-политика, очередь, RBAC, интервалы этапов 7–8). Decisions сохраняют происхождение решений, не создавая отдельного «журнала вопросов».

## ADR-004: Самодостаточность Walking Skeleton

- **Решение**: Walking Skeleton — самодостаточный контракт для реализации: полные HTTP-эндпоинты со статусами, JSON-схемы, SQL-сценарии, таблица интервалов, эдж-кейсы. Без «см. ТЗ» как единственной справки.
- **Почему**: док должен одинаково читаться любым разработчиком без обращения к исходникам. Самодостаточность проверяется checklist-ом в `walking-skeleton.md`.
- **Стек**: намеренно не зафиксирован (любой язык; REST + реляционная БД). WS описывает контракт, не реализации.

## ADR-005: Хранение токена — HttpOnly cookie

- **Решение**: для web-приложения токен хранится в HttpOnly/Secure кеуке (рекомендация диаграммы sq-1). localStorage для токена не используется (XSS-поверхность).
- **Почему**: безопасность по умолчанию; fallback для SPA без cookie-адаптера — Bearer в `Authorization` (допустимо в MVP, если эндпоинты аутентифицированы тем же middleware).

## ADR-006: Первичная загрузка словаря — сид-миграция

- **Решение**: базовый словарь по умолчанию поставляется сид-миграцией бэкенда (скрипт), а не только через админку. Пользователь скачивает словарь через API (WS-2).
- **Почему**: в ядре скелета (auth → учиться) админка отсутствует; без сида свежий деплой пуст, цикл обучения непроверяем. Импорт через админку — отдельный stretch-путь WS-4.
